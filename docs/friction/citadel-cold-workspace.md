# Citadel cold-workspace friction log

This run used Huyang for every repository file read, search, and content edit. Before creating this log I made eight successful Huyang calls: two workspace opens, three reads (one multi-file and one multi-window), one search, one multi-operation edit, and one language-server status probe. I then needed two attempts at the ninth logical operation, creating this file. I did not use `cat`, `head`, `sed`, `grep`, `find`, a heredoc, or a plain editor on repository file contents.

The first Huyang call opened the steward workspace with `overview=full`. It immediately showed 401 files, Go verification commands, and `reused=false`, making it clear that this was the Huyang clone intended for the friction log rather than Citadel. That response was useful and compact enough despite the full overview. I then cloned Citadel to `/tmp`, as the scenario preamble directs when the provided workspace is not the target repository. The first Git branch-creation attempt failed because cloning the shared source checkout inherited an already checked-out branch named `scenario/semantic-negative-fixture`; I had assumed the clone would start on the default branch. Inspection showed `origin/main` at the actual base and the inherited scenario branch at a different commit. Detaching at `origin/main`, deleting only the fresh clone's inherited local branch, and recreating it worked. This was not a Huyang failure, but it was startup friction and the scenario prompt's phrase “branch off its current default branch” did not match the source checkout's HEAD.

The cold Citadel `workspace_open` was the second Huyang call. It completed in about half a second, counted all 65 files, correctly detected `make check`, Python syntax, and `make test`, and clearly said project commands were untrusted. It also initially summarized semantic support as parser sections and said LSP should be probed. That was genuinely good orientation for a non-Go repository. The verification policy being untrusted was not a blocker because the task explicitly required the shell's `make check`, and I did not alter Huyang's machine-wide trust configuration.

A two-target `read` returned all 83 lines of `tests/validate_contracts.py` and all 16 lines of the Makefile in one usable response. This was the best call of the run: it exposed the validator's three relevant blocks, the exact output style, the fixture paths, and the mandated check without extra navigation.

My fourth Citadel-oriented call was a literal `search` for `"kind": "Mission"` under `fixtures/v1`. I expected JSON formatting with spaces, but the fixture stores object members compactly, so Huyang returned zero matches. The zero-result response was precise, but the guess cost a call and briefly created the strongest temptation to use `grep` or `rg` to discover the actual spelling. I stayed with Huyang and read the positive fixture path already named by the Makefile instead. That whole-file read was only 17 physical lines but 4,230 bytes because each record is a long compact JSON line; the answer was still manageable, though line-oriented sizing understates how much text a compact JSON fixture contains.

The multi-operation `edit_apply` was effective: one call copied the positive fixture, changed only the approval's fenced `graph_revision`, and made both Python replacements. It created the missing fixture directory automatically and reported both changed paths plus the Git staging command. The response also emitted six new Pyright errors saying the compiled schema validator was “not callable.” Those diagnostics appeared at the existing calls as well as the new one, even though the repository successfully executes that pattern. I had to read the changed source and run the real checks to separate those type-analysis false positives from actionable failures. This was the one reply I read twice, and the six diagnostic records were the largest amount of paid-for information I did not need.

The explicit language-server status probe clarified the cold state well: Pyright and `autotools_ls` attached, while all 15 JSON files had parser coverage but no JSON language server. Its suggested installation actions were understandable, but installing a JSON server would have expanded machine state and was unnecessary for this fixture-only task. A parallel two-window read then confirmed the changed Python loop and the exact mismatched Mission fields without redelivering either whole file. That targeted read was concise and useful.

Creating this friction log was the only Huyang operation that needed more than one try. I first called `edit_apply` with `kind=create_file`, path `docs/friction/citadel-cold-workspace.md`, the full content, and idempotency key `scenario6-create-friction-log`. I guessed that it would create the missing parent directory because the scenario explicitly said to create the directory with that operation, and because the same earlier multi-operation call successfully created `fixtures/v1/semantic-invalid` as part of `copy_file`. Instead it failed trying to open a temporary file under the absent directory: `no such file or directory`. The refusal's `next` list was empty, so it did not say how to recover. Huyang exposes no directory-creation operation. I therefore used the shell only for `mkdir -p docs/friction`, logged that exception here, and retried `create_file` with a fresh idempotency key; the retry succeeded. This is the one direct repository filesystem mutation performed outside Huyang, and it changed only the otherwise unrepresentable directory entry, not file content.

I wanted a shell `cat` once while preparing this report, because copying terminal output into prose would have been familiar, and I wanted `grep` once after the whitespace-sensitive JSON search missed. Neither was necessary. Repository reads stayed in Huyang, the fixture was created by Huyang's `copy_file` operation rather than `cp` or a heredoc, and this report's content was created with `edit_apply kind=create_file`.

The final `revision_diff` review was hard to use in both workspaces. Each response identified the correct changed paths and hashes but returned `diff_evidence_incomplete` with no patch: Citadel had an uncovered `wsrev_5` to `wsrev_6` gap after the shell verification, and Huyang had an uncovered `wsrev_2` to `wsrev_3` gap after the shell-created directory. I followed each response's suggestion and called `workspace_inspect view=status`. Those calls confirmed current revisions and policy state, but they returned large scheduler, pipeline, provider, and limit structures when I only needed a current baseline; most of those fields were not useful for the review. The known changed paths had already been read, and Git's own status plus the required checks supplied the remaining pre-commit evidence.
