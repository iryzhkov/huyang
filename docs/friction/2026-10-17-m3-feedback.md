## Spool additions

- `sub_codes` is a code-to-count object for batch read failures. The logger
  inspects `data.files` only: `data.entries` repeats those failures and must
  not double their counts. It handles both native map slices and decoded JSON
  slices. Successful batches omit the field.
- `has_results` is an explicit boolean on partial replies. A successful batch
  read target, delivered symbol handles, search hits, or revision diff records
  make it true. Coverage metadata, result counts without delivered records,
  recovery candidates, and error-only batch items do not. The logger reads
  container shapes without serializing source or provider payloads.
  The existing `ok` outcome classification is preserved; downstream reporting
  can distinguish partial-with-results using this additive field.
- `initialize` events carry `client_capabilities`, a sorted list of standard
  advertised top-level names: `elicitation`, `experimental`, `extensions`,
  `roots`, and `sampling`. An empty advertisement is recorded as `[]`.
  Capability values, nested feature switches, experimental keys and extension
  identifiers are never copied. Roots are detected from the SDK's nullable
  `RootsV2` field, so an empty roots object counts as advertised and a missing
  roots capability does not become a false positive.
- Receiving middleware observes successful legacy `initialize` and modern
  `server/discover` requests. Modern SDK clients do not send
  `notifications/initialized`, so that hook alone is insufficient.
  A per-server set keyed by SDK connection emits one event per connection,
  even if discovery is repeated. Reconnecting emits another event with the
  same adapter session or server instance. Entries are removed when their
  connection closes; disabled spooling allocates no connection tracking.
  Tool calls do not repeat capabilities. This introduces initialization lines
  in addition to tool-call lines; consumers counting calls should exclude
  `tool == "initialize"`.

## Privacy and test isolation

Batch logging copies only machine codes and counts, plus the result-presence
bit. It never copies target paths, source bodies, recovery arguments, capability
settings or other argument values into these fields. Existing project identity
remains the root basename. `workspaceRev` now returns immediately for every
non-absolute root, before touching Git or its cache, so `root: "."` cannot
record the daemon's checkout revision.

The service suite's existing `TestMain` redirects all spool output to a fresh
temporary directory. It now also sets `HUYANG_FRICTION=0`, overriding inherited
opt-in flags and enabled markers. Every existing opt-in service spool test was
reviewed: friction, retention and M1 diagnostic spool tests each set their own
temporary `HUYANG_FRICTION_DIR` before enabling writes. A subprocess regression
test verifies that inherited opt-in flags and an enabled developer-like spool
are overridden before client helpers run. M1 diagnostic files and tests remain
unchanged.

## Integration limits

- Stateless HTTP discovery emits a capability event on its ephemeral SDK
  connection; ordinary HTTP requests do not repeat it. Clients that skip
  discovery/initialization and send only per-request capability metadata have
  no handshake to record. The change does not infer a persistent identity
  from client names, HTTP headers, or adapter session IDs.
- Useful-result detection covers batch read, symbol_find, search, and revision_diff
  payloads. Other partial reply shapes conservatively record false; their mere
  metadata presence is insufficient evidence of useful results.
- The adapter random session fallback belongs to M2 prototype `75dff44` and
  is not duplicated here.
- The parent owns README integration and later homelab-cli reporting/transcript
  joins. No downstream changes, PR, push, merge, installation, service restart,
  fleet distribution, shared-roadmap edits or eval/Ollama access occur here.
